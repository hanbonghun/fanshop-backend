# 측정 0001 — 단일 재고 행의 처리량 상한

주문 플로우를 결제 승인까지 실제 PG 규격에 맞춘 뒤, "이 구조가 초당 몇 건까지 소화하는가"를 재고 소진 없이 측정했다.
목적은 성능 자랑이 아니라 **다음 개선을 어디에 해야 하는지 정하는 것**이다.

## 측정 조건

- 단일 개발 장비(macOS, Docker Desktop). 부하 생성기·애플리케이션 3개·MySQL·Kafka가 모두 같은 머신에서 동작한다.
- 재고 1억 개짜리 단일 상품(`productId=1`). 재고 부족 분기를 없애 **같은 행에 대한 경합만** 남긴다.
- 측정에 방해되는 항목만 끈다: `show-sql=false`, `management.tracing.enabled=false`, `logging.level.root=WARN`.
  Virtual Threads는 `local-dev` 기본값(on) 그대로 둔다.
- k6 v1.7.1, `tests/k6/inventory-contention.js`.

**절대 수치는 이 환경에 종속된다.** 결론으로 삼는 것은 절대값이 아니라 조건을 바꿨을 때의 상대 변화다.

## 실험 1 — `POST /orders` 처리량 곡선

VU를 올려가며 각 단계 20초씩 측정했다.

| VU | RPS | med(ms) | p95(ms) | p99(ms) | 5xx |
|---:|---:|---:|---:|---:|---:|
| 10 | 156.5 | 48.1 | 164.4 | 273.0 | 0 |
| 25 | 424.6 | 47.8 | 137.6 | 234.7 | 0 |
| 50 | **647.0** | 66.8 | 143.7 | 289.1 | 0 |
| 100 | 524.3 | 152.0 | 406.5 | 636.2 | 0 |
| 200 | 548.9 | 351.2 | 613.8 | 807.0 | 0 |
| 400 | 484.7 | 758.3 | 1120.3 | 1839.5 | 0 |

VU 50에서 647 RPS로 정점을 찍고, 그 뒤로는 **처리량이 늘지 않으면서 지연만 선형으로 증가**한다.
med는 66.8ms에서 758.3ms로 11배가 됐는데 처리량은 오히려 줄었다. VU 50 이상은 대기열만 길어지는 구간이다.

이 경로는 상품 조회(동기 HTTP) → 주문·Outbox 저장까지이며 **재고 행 잠금을 포함하지 않는다.**
재고 예약은 product-service가 Kafka로 비동기 처리하므로 따로 측정해야 한다.

## 실험 2 — 파이프라인 단계별 소화율

백로그가 쌓인 포화 상태에서 각 단계의 소화율을 샘플링했다.

| 단계 | 소화율 | 무엇이 제약인가 |
|---|---:|---|
| `POST /orders` 수용 | 647/s | (정점) |
| Outbox 릴레이 (기본) | ~97/s | `BATCH_SIZE=100` × 1초 폴링 — 구조적 상한 100/s |
| Outbox 릴레이 (폴링 100ms) | ~326/s | 폴링 주기를 낮추면 3.4배 |
| 재고 예약 (컨슈머 1) | ~31/s | 직렬 처리 |
| 재고 예약 (컨슈머 8) | ~24/s | 락 경합 |

릴레이의 100/s는 성능 특성이 아니라 **상수와 폴링 주기가 만든 값**이었다. 측정값 97/s는 그 계산과 일치한다.

## 실험 3 — 동시성을 올리면 빨라지는가

`order.created` 파티션을 1 → 8로 늘리고 컨슈머 동시성도 8로 올렸다.

**처리량이 늘지 않았다. 오히려 줄었다 (~31/s → ~24/s).**

측정 중 MySQL의 InnoDB 행 잠금 지표는 다음과 같았다.

| 지표 | 값 |
|---|---:|
| `Innodb_row_lock_waits` | 11,662 |
| `Innodb_row_lock_time` | 360,294 ms |
| `Innodb_row_lock_time_avg` | **30 ms** |
| `Innodb_row_lock_time_max` | 3,999 ms |

이벤트당 처리 시간이 약 32ms인데 **평균 락 대기가 30ms**다. 처리 시간의 대부분이 대기다.
스레드를 8배로 늘려도 같은 행을 통과하는 속도는 변하지 않고, 대기 비용만 추가된 것이다.

## 결론

1. **API는 647건/초를 받지만 재고 예약은 31건/초를 소화한다. 약 21배 격차다.** 그 사이는 전부 대기열에 쌓인다.
2. **병목은 재고 행 하나이고, 스레드를 늘려서 넘을 수 있는 종류가 아니다.** 컨슈머를 8배로 늘린 실험이 이를 직접 보여준다.
3. 다만 지금 구성(파티션 1·컨슈머 1)에서는 **그 행에 동시에 접근하는 스레드가 애초에 하나뿐이다.**
   `SELECT FOR UPDATE`는 다중 인스턴스에 대비한 장치이며, 현재 실행 조건에서는 경합을 막고 있지 않다.

## 다음에 무엇을 할 것인가

우선순위는 측정값이 정한다.

- **먼저 릴레이**: 100/s는 상수 하나로 정해진 값이라 가장 싸게 걷어낼 수 있다. `BATCH_SIZE`가 하드코딩이라 설정으로 빼는 것이 선행이다.
- **그다음이 재고 행**: 여기서부터는 스레드로 해결되지 않는다. 선택지는 세 가지이고 성격이 다르다.
  - 직렬화 지점을 더 싼 것으로 교체 (Redis 단일 스레드 원자 연산). 대신 RDB 트랜잭션을 잃고 대사가 필요해진다.
  - 재고를 여러 행으로 쪼개 경합을 분산.
  - 오버셀을 허용하고 사후 취소로 수습.
- 셋 중 무엇을 고를지는 오버셀 비용이 정한다. 한정판을 전제한 이 프로젝트에서는 정합성을 깎는 선택의 비용이 크므로,
  같은 플로우에 경로를 하나 더 만들어 두 선택을 나란히 측정하는 쪽이 맞다고 본다.

## 재현 방법

```bash
docker compose up -d mysql zookeeper kafka

# 측정용 기동 (SQL 로깅·트레이싱 off)
java -jar {product,payment,order}-service/build/libs/*.jar \
  --spring.profiles.active=local-dev \
  --spring.jpa.show-sql=false \
  --management.tracing.enabled=false \
  --logging.level.root=WARN

# 재고가 소진되지 않을 상품 시딩
INSERT INTO products (id,name,price,stock_quantity,reserved_quantity)
VALUES (1,'경합측정용',50000,100000000,0);

# 처리량 곡선
k6 run -e VUS=50 -e DURATION=20s -e JWT_TOKEN=$JWT_TOKEN tests/k6/inventory-contention.js
```

예약 소화율은 `product_db.processed_events`에서 `event_type='ORDER_CREATED'` 누적 건수의 증가율로 측정한다.
`reserved_quantity`는 만료에 따른 해제로 감소할 수 있어 소화율 지표로 쓰지 않는다.
만료 스위퍼는 `order.expiry.threshold-minutes`를 크게 잡아 꺼둔다.
