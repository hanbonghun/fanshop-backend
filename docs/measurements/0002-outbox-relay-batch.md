# 측정 0002 — Outbox 릴레이의 실제 상한

[측정 0001](0001-inventory-contention.md)에서 릴레이 소화율이 ~97/s로 나왔고, 이것이 `BATCH_SIZE=100 × 1초 폴링`이 만든
값이라는 것까지는 확인했다. 그렇다면 **설정을 풀었을 때 실제로 어디까지 가는가**를 재고, 배치 크기와 폴링 주기 중
어느 쪽을 움직이는 게 나은지 비교했다.

## 측정 조건

- 릴레이 단계만 격리한다. `outbox_events` 행을 SQL로 직접 심고 order-service만 띄운다.
  주문 API도 컨슈머도 개입하지 않으므로 발행된 메시지는 Kafka에 쌓이기만 한다.
- 시드 20만~25만 건(PENDING). 측정 창 동안 물량이 마르지 않게 한다.
- 기동 후 발행이 시작된 것을 확인하고 **20초 워밍업** 뒤 30초 창에서 잰다.
- 단일 개발 장비(macOS, Docker Desktop). 절대값은 환경 종속이다.

## 결과

| batch | delay | 이론 상한 | 실측 | 달성률 |
|---:|---:|---:|---:|---:|
| 100 | 1,000ms | 100/s | **90/s** | 90% |
| 1,000 | 1,000ms | 1,000/s | 666/s | 67% |
| 100 | 100ms | 1,000/s | 616/s | 62% |
| 1,000 | 100ms | 10,000/s | 1,966/s | 20% |
| 2,000 | 100ms | 20,000/s | **2,600/s** | 13% |
| 4,000 | 100ms | 40,000/s | 2,400/s | 6% |

**실측 상한은 2,400~2,600/s 부근에서 평탄해지고, batch 4,000에서는 오히려 줄었다.**
배치를 키우면 한 틱의 트랜잭션이 길어져 `FOR UPDATE SKIP LOCKED`로 잡은 행과 DB 커넥션을 그만큼 오래 붙드는데,
어느 지점부터는 그 비용이 배치 확대의 이득을 상쇄한다.

## 배치와 폴링 중 무엇을 돌릴 것인가

이론 상한이 같은 두 조합을 비교하면 차이가 거의 없다.

| 조합 | 이론 상한 | 실측 |
|---|---:|---:|
| batch 1,000 / 1,000ms | 1,000/s | 666/s |
| batch 100 / 100ms | 1,000/s | 616/s |

**어느 쪽을 돌리든 비슷하다.** 측정 전에는 "백로그 소화에는 배치가 유리하고 잦은 폴링은 빈 쿼리만 늘린다"고
예상했지만, 포화 상태에서는 그 차이가 드러나지 않았다. 큐가 비어 있을 때의 낭비는 이 측정에서 다루지 않았으므로
잦은 폴링의 비용은 여전히 미검증으로 남는다.

## 그래서 기본값을 올릴 것인가 — 올리지 않는다

릴레이의 실제 상한은 2,600/s로, 기본값 90/s의 약 29배 위다. 릴레이는 병목이 **아니었다.**

그런데 파이프라인 전체를 보면 이야기가 달라진다.

| 단계 | 소화율 |
|---|---:|
| `POST /orders` 수용 | 647/s |
| Outbox 릴레이 (기본 100/1s) | 90/s |
| Outbox 릴레이 (상한) | **2,600/s** |
| 재고 예약 | **31/s** |

**릴레이를 풀어도 end-to-end 처리량은 1건도 늘지 않는다.** 뒤에 31/s가 있기 때문이다.
늘어나는 것은 처리량이 아니라 대기열의 위치뿐이다 — `outbox_events` 테이블에 쌓이던 것이 Kafka로 옮겨간다.

오히려 지금 기본값을 올리면 손해에 가깝다. 관측 가능한 DB 테이블에 쌓여 있던 백로그가 브로커 안으로 들어가
눈에 덜 띄게 되고, 소비되지 않는 메시지로 브로커 저장소만 쓴다.

**기본값 100/1초를 그대로 둔다.** 바꿀 이유는 재고 예약 쪽을 먼저 풀어낸 뒤에 생긴다.

## 측정하면서 틀렸던 것

기록해 둘 가치가 있는 실수가 두 개 있었다.

**1. 코드를 고치고 jar를 다시 빌드하지 않았다.** 배치 크기를 설정으로 뺀 뒤 이전 jar로 측정해서,
batch 100과 1,000이 똑같이 ~90/s로 나왔다. "배치를 키워도 효과가 없다"는 그럴듯한 결론이 나올 뻔했다.
`batch-size=7`로 두고 발행량이 7의 배수로 증가하는지 확인하고 나서야 설정이 적용되지 않았다는 것을 알았다.
**설정을 바꾸는 실험은 그 설정이 실제로 적용됐는지 먼저 확인해야 한다.**

**2. 워밍업을 측정 창에 포함시켰다.** 기동 5초 뒤부터 재니 batch 1,000/100ms가 366/s로 나왔는데,
20초 워밍업 후 다시 재니 1,966/s였다. 5배 차이다. 첫 측정만 보고 "폴링을 빠르게 하면 오히려 느려진다"는
결론을 낼 뻔했다.

두 경우 모두 **틀린 결과가 그럴듯했다**는 점이 문제다. 이상하지 않은 숫자는 검산하지 않게 된다.

## 재현 방법

```bash
# outbox_events에 PENDING 행을 직접 심고 order-service만 띄운다
docker exec fanshop-mysql mysql -uroot -proot order_db -e "
INSERT INTO outbox_events (created_at, event_type, payload, published_at, retry_count, status)
SELECT NOW(6), 'ORDER_CREATED',
       CONCAT('{\"orderId\":', n, ',\"memberId\":1,\"productId\":1,\"quantity\":1,\"totalPrice\":50000}'),
       NULL, 0, 'PENDING'
FROM (WITH RECURSIVE seq(n) AS (SELECT 1 UNION ALL SELECT n+1 FROM seq WHERE n < 200000) SELECT n FROM seq) t;"

java -jar order-service/build/libs/order-service-*.jar \
  --spring.profiles.active=local-dev \
  --outbox.relay.batch-size=1000 \
  --outbox.relay.fixed-delay=100 \
  --order.expiry.threshold-minutes=999999
```

발행이 시작된 것을 확인하고 20초 기다린 뒤, `status='PUBLISHED'` 건수의 30초간 증가량으로 소화율을 계산한다.
